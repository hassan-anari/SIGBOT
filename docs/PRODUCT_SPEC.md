# Product Specification — Telegram Signal Management Bot

## Document Status

This document defines the final, approved product scope and must be used as the **Source of Truth** for development.

No feature, role, workflow, state, or business rule outside this document may be added to the project without explicit approval.

---

## Approved Initial Storage Architecture

SQLite is the primary permanent database for local development, automated tests,
and the initial production deployment. Redis stores ephemeral runtime state only;
PostgreSQL is not currently required. The initial deployment assumes one active
application instance, one Redis-leased Telegram poller, and a SQLite file on local
persistent storage with regular safe backups.

The SQLAlchemy repository, application-service, and Alembic boundaries remain
separate from domain and Telegram logic so PostgreSQL can be introduced later if
operational requirements change. PostgreSQL should be reconsidered only for
multiple application instances or concurrent workers, high write concurrency,
remote database hosting, replication, large analytical workloads, or requirements
that exceed a single local database file.

---

# 1. Product Definition

The system is a comprehensive Telegram bot for creating, publishing, monitoring, and reporting trading signals.

Signalists create Market or Limit signals through the bot. The system retrieves market prices, establishes the authoritative Entry, detects TP, SL, and explicit Risk Free lifecycle events, generates images, and publishes eligible approved updates. Historical Breakeven events remain readable compatibility data only.

The system also maintains complete trade history, Signalist performance statistics, Win Rate, and theoretical profit.

---

# 2. System Roles

## Phase 2 — Warm-up messages

Active Signalists have a one-tap Warm-up action. It creates standalone, text-only
messages for their currently assigned active destinations. A rolling one-hour
cooldown is global per destination across all Signalists and begins at the durable
SQLite reservation, regardless of the later delivery outcome. Text resolution uses
destination override, then global Main Admin override, then the built-in template.
Warm-up messages neither consume daily Signal capacity nor participate in Signal
reply chains or the Signal lifecycle.

## 2.1. Main Admin

The Main Admin has access to system-wide administrative functions and is responsible for managing:

- Signalists
- Destinations
- Signalist-to-destination assignments
- Exchange priority for each destination
- Daily destination limits
- Default and destination-specific templates
- Comprehensive and individual reports
- Service and API status
- Outage and recovery alerts

Reports are generated only when requested by the Main Admin.

## 2.2. Signalist

A Signalist can:

- Create a new signal.
- Enter signal information.
- View the Entry validation result.
- Receive detected events for their own signals.
- Approve publication of updates.
- View their own performance record and statistics.

A Signalist:

- Does not see destinations.
- Is not informed of the number of compatible destinations.
- Does not select an exchange, except in the exceptional flow for a Symbol outside the shared list.
- Does not upload images.
- Does not enter free-form descriptions.

---

# 3. Signalist Status

A Signalist has one of three statuses:

- Active
- Inactive
- Archived

## 3.1. Active Signalist

An active Signalist can perform all permitted actions, create new signals, and approve and publish signal updates.

## 3.2. Inactive Signalist

An inactive Signalist:

- Cannot perform new actions.
- Cannot create new signals.
- Cannot approve or publish updates for previous signals.
- Has previous signals monitored only in the background.
- Has the results of those signals recorded in the Signalist's statistics and performance record.
- Has no updates from those signals sent to destinations.

## 3.3. Archived Signalist

Archiving is a soft delete. All Signalist history, signals, results, and reports remain preserved.

---

# 4. Signal Information

The Signalist selects Market or Limit and supplies Symbol, Long/Short direction,
leverage, one or more ordered TPs, and SL. Market Entry is the accepted creation
reference. Limit Entry is the exact requested Decimal price. There is no Entry
range, scaled Entry, free-form description, Signalist-uploaded image, or exchange
order execution. All images are generated by the system.

## 4.1. Market lifecycle and Entry

1. Symbol selection captures reference snapshot P0.
2. Final Market creation captures a fresh P1.
3. `abs(P1 - P0) / P0 × 100` must be at most exactly **0.70 percent**.
4. The accepted creation reference is persisted as the authoritative Market Entry.
5. The complete Stage-One record enters `PENDING_DETAILS`; Stage Two adds leverage,
   ordered TPs, and SL before activation/publication proceeds.

## 4.2. Limit lifecycle and Entry

A complete Limit is persisted only after all trade details are configured. Its
requested price is authoritative: LONG must be strictly below the fresh current
reference and SHORT strictly above it. A Limit has no expiration and transitions:

```text
PENDING_ENTRY → ENTRY_TRIGGERED → ACTIVE
```

The sampled trigger comparison is inclusive, durable, and irreversible. Triggering
does not activate monitoring: the Signalist must explicitly activate, with Active
Signals providing the recovery action. Pre-activation cancellation is allowed.
The Pending announcement is text-only. Destination admission consumes the shared
Tehran daily capacity and acquires the normal Symbol Trade Lock; activation consumes
no second slot or lock and replies only to the exact definitely-sent Pending parent.
There is no late destination backfill. Destination facts remain hidden from the
Signalist.

# 5. Market Data and Reference Price

## 5.1. Composite core and optional enrichment

Shared eligibility is the Futures/Perpetual intersection of **Ourbit, Toobit, and
LBank**. WEEX is an optional fourth enrichment source. Missing WEEX support never
removes a core Shared Symbol. Historical Composite Signals retain their exact three
persisted mappings; new Composite Signals persist the three core mappings and an
optional WEEX mapping, for either three or four mappings total.

WEEX uses public Contract API V3 only. Its normal price source is `markPrice` from
one bulk `/capi/v3/market/premiumIndex` request per polling cycle. Chainura does not
use per-Signal WEEX polling, WebSockets, or candle reconstruction. Optional WEEX
catalog failure does not disable Shared Search, and runtime recovery retries the
missing optional catalog autonomously without repeatedly refreshing a ready catalog.

## 5.2. Deterministic reference policy

- Fewer than two fresh valid sources: unresolved; no Reference Price.
- Exactly two: use the arithmetic mean only when spread is within the configured
  threshold; otherwise unresolved.
- Exactly three: use the median with the current agreement and clear-outlier
  safeguards; without an agreeing shape, unresolved.
- Exactly four: when all agree within threshold, average the two middle sorted
  prices. When exactly one source is a unique outlier, discard it and use the
  median of the remaining three. With conflicting clusters or no unique agreeing
  quorum, unresolved with no Reference Price.

Persisted price-source types are Composite, Ourbit Only, Toobit Only, LBank Only,
and WEEX Only. Single Exchange mode may use any one of those four exchanges and is
publishable only where that exact exchange occurs in Destination priority.

# 7. Symbol Outside the Shared List

If a Symbol is not in the shared list:

1. The Signalist selects the “Search Outside the List” button.
2. The Signalist selects an exchange.
3. The Signalist enters the asset name or Symbol.
4. The bot searches only within the API response of that exchange.
5. The bot displays similar results.
6. The Signalist selects the correct contract.
7. The signal is created in Single Exchange mode.
8. Only that exchange's price is used for validation and monitoring.
9. Only that exchange's image is generated.
10. Only destinations that support that exchange can receive the message.

# 8. Destinations

Each destination contains the following information:

- Internal name
- Chat ID
- Type: channel or group
- Access level: public or private
- Status: active or inactive
- Exchange priority
- Daily limit
- Assigned Signalists
- Optional destination-specific template for each exchange

## 8.1. Exchange Selection for a Destination

Each destination stores a normalized, non-empty ordered priority of one to four
supported exchanges. Existing priorities remain unchanged until Main Admin edits
them; WEEX is never inserted automatically. Publication freezes the first priority
exchange actually present in the Signal's durable source snapshot. A Single
Exchange Signal requires that exact exchange and never substitutes another.

## 8.2. Destination Trade Lock

Initial-publication admission permits at most one open trade for each persisted
canonical Symbol in each destination. The rule is destination-specific, global
across Signalists, and independent of direction and Signal mode. An admitted
`PENDING_DETAILS` Signal occupies the slot immediately. A blocked destination is
permanently skipped for that Signal and is never backfilled after the owner closes;
the blocked Signal itself remains valid, is monitored, and counts normally.

Pending/retrying/template-blocked, `sent`, and `delivery_unknown` Initials retain
occupancy while their Signal is open. A definite pre-send or delivery failure
releases occupancy, as does durable cancellation, final TP, SL, or Risk Free hit.
Historical accepted Breakeven rows retain their compatibility behavior. Warm-up messages neither inspect nor modify destination trade locks.

Example:

1. WEEX
2. Ourbit
3. Toobit
4. LBank

For a Composite signal, the system selects the first available exchange according to the destination's priority list.

If no compatible version exists, that destination does not receive the message.

## 8.3. Phase 4 Registration and Presentation

- Main Admin creates a Signalist using only the numeric Telegram user ID and display
  name. Telegram username is not collected or displayed.
- A Destination is registered from a normalized Telegram Chat ID. Its title and
  channel/group type are discovered from Telegram; private chats are unsupported.
- The bot must already be the destination owner or an administrator. This status is
  checked during discovery and again immediately before persistence, outside the
  database transaction. No test message is sent.
- Destination access level and daily signal limit remain manually configured. The
  daily limit is configuration-only in Phase 4.
- Telegram-visible dates use the Jalali calendar and Tehran local time, while stored
  timestamps remain aware UTC. Internal database IDs are not presented to users.

Even if a signal is sent to no destination, it is still:

- Recorded.
- Monitored.
- Included in the Signalist's performance record.
- Hidden from the Signalist in terms of destination count or the absence of destinations.

## 8.2. Destination Rules

- `#پیامک` is fixed.
- It is added only to the initial message for a private destination.
- Updates do not include `#پیامک`.
- The daily limit applies only to the initial message.
- Updates do not consume daily capacity.
- An inactive destination receives neither an initial message nor updates.
- An update is sent only to a destination that successfully received the initial message.

# 9. Templates and Image Generation

## 9.1 Initial-card financial snapshot

The final successful Entry validation persists its immutable, exact Decimal
per-exchange source-price snapshot with the Signal. Composite signals retain the
two or three healthy sources used by validation; Single Exchange signals retain
exactly the selected exchange. Initial image generation never refreshes prices.

For an exchange card, Reference Price remains the persisted validation reference,
while Display Price is that exchange's persisted snapshot price. Initial leveraged
PnL uses the temporary formula in section 12 with persisted Entry, Display Price,
direction, and leverage, without intermediate rounding. The visible card symbol is
the persisted canonical symbol; native symbols remain available only for exchange
integration and local Toobit logo lookup.
Toobit logo files use one traversal-safe canonical logo key (for example,
`TONUSDT`) derived at the logo-store boundary; the hyphenated native/API identity
(for example, `TON-SWAP-USDT`) remains unchanged for exchange calls.

Signals created before the initial-price migration are detected as legacy rows
without snapshots and cannot be rendered as initial cards. The system must not
fabricate their snapshot from Reference Price or perform a fresh market request.

Each exchange has one default templates.

Each destination may have a destination-specific template for each exchange.

Template selection priority:

1. The destination-specific template for that destination and exchange
2. The default template for that exchange

All templates use a shared data model. The backend produces the same information, and the Renderer places it onto the relevant design.

All of the following events have images:

- Initial signal
- TP1
- TP2 and subsequent TPs
- SL
- Risk Free hit
- Historical Breakeven updates remain renderable for compatibility only.

# 10. TP and SL Lifecycle

## 10.1. TP Ordering

- TPs are recorded only in sequence.
- TP2 is not processed as an independent stage before TP1.
- The highest reached TP is the signal's final result.
- TP profits are not added together.
- A previous profit is replaced by the profit of a higher TP.

## 10.2. SL Before TP1

- SL is monitored before TP1.
- If SL occurs before TP1, the result is Loss.

## 10.3. State After TP1

- Once TP1 is reached, the signal is considered a Win.
- After TP1, SL is no longer checked.
- Only subsequent TPs are monitored.
- If price reaches SL after TP1, the result remains TP and Win.

## 10.4. Crossing Multiple TPs in One Poll

If price crosses multiple TPs in one poll:

- Intermediate states are considered traversed in internal data.
- The latest detectable TP is stored as the latest result.
- If a previous TP has not yet been published, it is no longer published.
- Only the latest valid update is presented for publication.

---

# 11. Risk Free and historical Breakeven compatibility

New Signals do not generate automatic `BREAKEVEN` events or contextual Breakeven
prompts. After a detected TP, the Signalist chooses an eligible explicit position
action. Risk Free moves the effective stop to persisted Entry without immediately
closing volume. If price later reaches Entry while Risk Free is active, the durable
event is `RISK_FREE_HIT`; all remaining fraction closes and that slice contributes
exact zero ROI.

`BREAKEVEN`, `COMPLETED_BREAKEVEN`, old prompt records/routes, and historical
report rows remain readable solely for backward compatibility. Their schema is not
removed, but they are not an active workflow for newly created Signals.

---

# 12. Temporary Profit Formula

Until the final formula is provided, the current formula is used.

## 12.1. Long

```text
Raw Profit % =
(Result Price - Entry Price) / Entry Price × 100
```

## 12.2. Short

```text
Raw Profit % =
(Entry Price - Result Price) / Entry Price × 100
```

## 12.3. Temporary Leveraged Return

```text
Leveraged ROI % = Raw Profit % × Leverage
```

Rules:

- For TP, the TP price itself is the basis of calculation.
- For SL, the SL price itself is the basis of calculation.
- For historical Breakeven compatibility rows, the result is zero.
- Fees are not calculated.
- Funding is not calculated.
- The formula must be implemented in an independent service or function so it can later be replaced without changing other parts of the system.

---

# 13. Win Rate

Result definitions:

- Reaching TP1 or higher: Win
- Reaching SL before TP1: Loss
- Historical Breakeven compatibility rows: Neutral

Formula:

```text
Win Rate = Wins / (Wins + Losses) × 100
```

Historical Breakeven reporting:

- Is displayed in the total trade count.
- Is excluded from the Win Rate denominator.

# 14. Signal and Update Publication

When an event is detected:

1. The result is recorded in the system.
2. The corresponding image is generated.
3. The Signalist is notified.
4. A button to publish to destinations is displayed.
5. After Signalist approval, the message is sent.

For an inactive Signalist:

- The publication stage does not occur.
- The result is recorded only in internal statistics.

## 14.1. Reply Chain

Replies form a chain:

- TP1 replies to the initial message.
- TP2 replies to TP1.
- TP3 replies to TP2.

If an event was not published, the next event replies to the last message that was actually published.

- Immediately alert the Main Admin

- After the active runtime acquires the Telegram poller lease, it starts a

- Rendering performs deterministic local lookup only. Renderers never access the

- Metadata or individual-image API failures are logged and remain non-fatal to
  Telegram polling; a later scheduled iteration retries unavailable logos.

# Phase 5A — Signal Creation and Rendering Boundary

Active Signalists create Composite Signals from the three-exchange Shared core,
optionally enriched by WEEX, or Single Exchange Signals from an exact verified
Ourbit, Toobit, LBank, or WEEX contract. Market calls occur outside database
transactions. The current staged Market flow persists Stage One as
`PENDING_DETAILS`; a complete Limit is persisted as `PENDING_ENTRY`.

Market creation captures P0 at Symbol selection and fresh P1 at final creation;
maximum accepted drift is exactly 0.70 percent, and the accepted creation reference
is authoritative Entry. Limit Entry is the requested Decimal price. Opaque creation
tokens keep creation idempotent, and short transactions recheck Signalist status
and atomically store each durable aggregate and its exact native mappings.

The rendering contract remains separate from signal creation. For the initial open
card, Entry is the exact persisted user value, Reference Price remains the final
validation reference, and Display Price/PnL derive deterministically from the
selected exchange's persisted final-validation source snapshot as specified in
section 9.1. Elapsed duration is zero. TP and SL are retained for a future caption
and are not card-layout fields. Ourbit displays elapsed/open time (`00H 00M`
initially), while Toobit and LBank display the externally supplied render time
converted to Asia/Tehran. Renderers receive all clock values; they do not read a
clock. Approved coordinates, fonts, templates, and layout tuning remain unchanged.

## Phase 5A finalized image specifications

The centralized initial-card canvas specifications are Ourbit 1080×1148 PNG,
Toobit 942×1010 PNG, LBank 830×1005 PNG, and WEEX 1000×1000 PNG. Long and Short use the same
exchange-specific dimensions. WEEX has a functional first-pass declarative layout. Main Admin may install a
WEEX default PNG and Destination-specific override under the same fallback rules
as other exchanges. Exact WEEX coordinates and typography are intentionally tuned
through Renderer Lab without changing production business logic; they are not
pixel-final.

# Phase 5C — Durable Initial Publication

Final confirmation atomically stores a new Signal, its immutable source-price snapshots, and exactly one SQLite initial-publication request. Publication is asynchronous and never discloses destination eligibility, counts, limits, templates, or failures to the Signalist. Historical Signals without an explicit request are not retroactively published.

The worker snapshots active assigned destinations, freezes the first priority exchange that is present in the persisted source-price snapshot, and rechecks destination activity and assignment immediately before delivery. Destination priority contains one to four exchanges and is never automatically extended. Single Exchange Signals require their exact exchange in that frozen priority; no substitute exchange is selected. SQLite daily slots, keyed by destination and the Asia/Tehran calendar date, atomically reserve initial-message capacity. Successful and delivery-unknown sends retain their slot; definite pre-send/render/Telegram rejection failures release it. Phase 6 updates do not use these slots.

Every destination is rendered independently with its configured override or exchange default. Main Admin template uploads are complete PNG documents (not recompressed photos); override removal falls back to the default. Missing templates block only the affected row. Generated `initial-*.png` files are caller-owned until send completion and are cleaned on every outcome; startup removes only owned initial-output patterns.

Initial captions contain the canonical Symbol, direction, exact Entry, leverage, ordered TPs, and SL using HTML escaping and explicit LTR isolation. Private destinations alone receive the fixed initial `#پیامک` hashtag. Telegram message IDs are persisted. A send is durably marked `sending` before the API call; timeout, connection interruption, or restart in that state becomes `delivery_unknown` and is never automatically resent because Bot API photo sends have no durable idempotency key.

Runtime recovery precedes worker intake. Shutdown stops polling, drains the publication worker, closes `InitialImageService`, then releases infrastructure and finally unregisters production renderers. Phase 6 remains responsible for current TP/SL/Risk-Free lifecycle detection, approval and update publication, historical Breakeven compatibility, reports, and outage alerts.

# Phase 6A — Monitoring and Signalist Event Decisions

Phase 6A automatically detects ordered TP events and coherent effective-stop hits
from sampled current prices. Configured threshold, observed event-time reference,
exact Decimal ROI, and source prices are separate durable facts. There is no candle
or wick reconstruction.

Current TP decisions use explicit position actions. At an eligible intermediate TP,
the Signalist may select Normal, one-time Risk Free, one-time Save Profit 50%, or
Full Close. Risk Free and Save Profit 50% are independent. Normal closes no
intermediate fraction; Save Profit 50% closes half the remaining fraction; Risk
Free moves the effective stop to Entry; Full Close closes all remaining fraction.
Final TP requires explicit action, and final Normal closes all remaining volume.
SL closes remaining volume unless Risk Free is active; an Entry hit while Risk Free
is active produces `RISK_FREE_HIT` and exact zero ROI for the remaining slice.
Weighted position accounting uses Decimal end-to-end.

Automatic Breakeven prompt generation is retired for current Signals. Historical
Breakeven events, terminal states, prompts, routes, and reports remain readable.
The owning active Signalist receives durable event/action notifications; inactive
or archived owners receive none while background result recording continues.

Shared Search uses the three-exchange core and optional fresh WEEX enrichment under
the deterministic two/three/four-source policy in section 5. Single Exchange search
supports all four exchanges. Each refresh is batched and stale/unavailable prices
cannot advance creation or monitoring.

## Phase 6B — Approved Update Publication and Reply Chains

Phase 6B publishes approved current TP/SL lifecycle updates and remains able to publish already-existing historical Breakeven candidates for compatibility. Signalist approval is durable publication intent only: the approval transition and one update-publication request are committed atomically, duplicate approvals do not create duplicate requests, and publication results remain hidden from the Signalist.

Update requests wait for the Phase 5 initial-publication lifecycle. Planning uses only destinations with a confirmed initial `sent` publication and a positive Telegram message ID; failed, unknown, blocked, skipped, or unsent initial rows are not eligible. Updates do not consume initial-publication daily-capacity slots.

For Composite events, each destination freezes the first exchange in its priority list that has a persisted event-time source-price snapshot. For Single Exchange events, only the Signal's selected exchange is compatible. No market request is made to reconstruct or refresh event prices.

Update images reuse the same current destination override/default template hierarchy and the existing exchange geometry. There are no update-specific templates or event-specific backgrounds. The image uses the persisted Signal identity, Entry, direction, leverage, TP/SL compatibility fields, event observed reference price, selected exchange event source price, and the event occurrence time. TP/SL PnL is calculated from original Entry and selected event-time display price with Decimal; historical Breakeven renders zero PnL by compatibility rule.

Destination update captions are centralized, concise Persian HTML captions with explicit BiDi isolation. They include only canonical Symbol, event reference price, event ROI (or zero for historical Breakeven compatibility), and TP index when applicable. Updates never include `#پیامک`, destination names/counts, source exchange, approval questions, internal IDs, or Signalist usernames.

The Reply Chain is per `(signal_id, destination_id)`. The first successful update replies to the confirmed initial message; each later successful update replies to the latest confirmed successful update for that same destination. Declined, skipped, failed, blocked, superseded, and `delivery_unknown` rows are not chain parents. Per-destination chains may diverge after mixed outcomes.

If a newer TP is detected before an older TP update is actually published to a destination, the older unsent TP delivery is durably superseded and must not be revived by restart. Already sent lower-TP messages remain in the real chain.

Update delivery persists retry state, attempts, sanitized error categories, selected exchange, reply target, Telegram message ID, sent time, and template identity when available. Ambiguous Telegram delivery becomes `delivery_unknown` and is not retried automatically. Template mutations unblock both initial and update `blocked_template` rows. Runtime recovery reclaims stale rendering/planning states, marks stale sending as unknown, reconciles approved candidates missing requests, and drains update work before closing shared rendering resources.

Reports, Win Rate screens, outage/recovery alerts, and final Phase 6 acceptance remain Phase 6C responsibilities and are not implemented in Phase 6B.

# Phase 6C — Main Admin Reports, API Health Alerts, and Final Phase 6 Acceptance

Phase 6C completes Phase 6. Reports remain Main Admin-only and on-demand; there are no scheduled reports, Signalist-visible reports, or destination reports. Report periods use Asia/Tehran calendar days and Signal creation time. Selected Tehran dates are converted into `start_utc <= signals.created_at < end_exclusive_utc`. Supported periods are today, last seven days including today, last thirty days including today, and inclusive Gregorian custom ranges entered as `YYYY-MM-DD`.

Report summaries include total Signals, active Signals, resulted Signals, Wins, Losses, historical Breakevens, Win Rate, theoretical ROI totals/averages/extremes, highest-TP distribution, Composite/Single Exchange counts, confirmed-published count, and unpublished count. Win Rate is `wins / (wins + losses) × 100`; Historical Breakevens and active no-result Signals are excluded, and an empty denominator displays `—`. Decimal is used end-to-end. Theoretical ROI is persisted highest-TP ROI for Wins, persisted SL ROI for Losses, exact zero for historical Breakeven, and excludes active no-result Signals. Confirmed publication means at least one Phase 5 initial destination publication has status `sent` with a positive Telegram message ID.

Trade history is paginated at ten rows, ordered by `created_at` descending and Signal ID descending. Rows show internal Signal ID, Signalist display name only for all-Signalists scope, canonical Symbol, direction, Tehran creation time, Composite or Single Exchange source, current state, highest TP, theoretical ROI, and confirmed-published yes/no. Destination details, Chat IDs, raw errors, and publication delivery internals are never displayed.

Durable API health independently monitors exactly eight services:
`ourbit_prices`, `ourbit_catalog`, `toobit_prices`, `toobit_catalog`,
`lbank_prices`, `lbank_catalog`, `weex_prices`, and `weex_catalog`. Service health
stores `unknown`, `healthy`, `degraded`, or `down`, timestamps, counters, sanitized
error category, and current incident. Alerts remain a durable outbox with initial,
repeat, and recovery kinds. A WEEX catalog outage is optional to Shared core and
never makes the healthy core Shared Search unavailable; missing optional catalog
recovery is autonomous.

Only `down` opens an incident and triggers repeating alerts. `degraded` is durable and visible to Main Admin but does not open an outage incident. The first down transition creates one incident and immediate alert, repeated down observations update the same incident, each due scheduler cycle creates at most one repeat alert and advances the next repeat by 60 seconds, and recovery closes the incident and creates one recovery alert. Sent and delivery-unknown alerts are never resent. There is no catch-up burst after downtime or restart.

Outage handling is safe: one down price source still allows Composite operation with two fresh agreeing sources, two down price sources pause Composite validation/monitoring, and loss of every usable price source produces no Composite confirmation or new monitoring event. Single Exchange Signals continue only when their selected exchange has usable pricing. Catalog outages are independent from price-service health and do not stop monitoring of already-persisted Signals when valid prices exist. After recovery, monitoring resumes from current data only; historical candles are not queried and missed events are not reconstructed or backdated.

# Phase 4B — Position Actions and Risk Free Lifecycle

A confirmed TP is decided by its owning active Signalist with one durable position
action. Intermediate targets offer Normal, one-time Risk Free, one-time Save Profit
50%, and Full Close; the final target offers only Normal and Full Close. Risk Free
and Save50 are independent and may be selected in either order. Normal leaves an
intermediate position unchanged, final Normal closes all remaining volume, Save50
closes exactly half of the then-remaining fraction, and Full Close is terminal at
any TP.

All closures use the Phase 4A Decimal reducer. For example, Save50 at +20 realizes
+10; a later SL at -10 on the remaining half contributes -5, producing a +5 final
weighted ROI. A later Risk Free hit contributes zero, preserving the earlier +10.
Terminal result kind is derived from this weighted total rather than the last event.

Risk Free moves the effective stop to the persisted Entry. Once active, the original
SL is ignored and a coherent LONG price at or below Entry (or SHORT price at or
above Entry) closes all remaining volume as `RISK_FREE_HIT`. Without active Risk
Free, the original SL remains monitored after TP1. The old favorable-move/Entry-zone
Breakeven prompt generator is retired; historical Breakeven data remains readable.
A detected final TP waits for Signalist action and cannot be superseded by SL.

Every accepted TP action first publishes the normal `TP_HIT` image. Risk Free,
Save50, and Full Close text follows only a definitely sent image and replies to its
Telegram message ID. Failed or delivery-unknown TP images never cause a guessed or
standalone follow-up. Final Normal, Full Close, SL, Risk Free hit, and cancellation
release destination trade locks when product state becomes terminal; Telegram
publication success does not control that release.

# Phase 5 — Durable Limit Orders

The earlier Market-only wording describes the existing Market path and is retained
for its compatibility contract. This approved phase adds `LIMIT` alongside
`MARKET`. Market behavior remains unchanged.

A complete Limit is persisted in `PENDING_ENTRY`, transitions irreversibly to
`ENTRY_TRIGGERED` when a sampled Chainura reference price reaches its requested
entry, and becomes `ACTIVE` only after explicit owner activation. It has no
expiration and never places an exchange order. LONG entries must be strictly below
the fresh confirmation reference; SHORT entries strictly above it. Decimal is used
end-to-end, TP/SL are based on the requested entry, and that entry remains the
trade's authoritative entry after triggering and activation.

The pending text announcement is each destination's admission point. It consumes
one Tehran-day Initial capacity slot and acquires the existing global destination
Symbol Trade Lock. Activation consumes neither again and may publish only to a
destination whose pending announcement is definitely sent, as a reply to that
known message. There is no late backfill or standalone fallback for a missing or
ambiguous reply parent. Pending and triggered Signals are operationally open and
may be cancelled; no TP/SL or performance accounting occurs before activation.

SQLite durably stores triggers, outboxes, capacity, and locks. Monitoring consumes
the shared batched price cache and current sampled reference prices; it does not
use WebSockets, candle high/low reconstruction, or per-Signal REST polling.
Interrupted sends become `delivery_unknown` and are not blindly repeated.
Telegram rate limits remain retryable until their explicit delay, while definite
rejections use normalized privacy-safe categories rather than raw Telegram text.
